1. Purpose

Pre-authorization lets a contracted provider confirm before treatment that a planned benefit is covered for a member, and reserves the estimated amount against that benefit's remaining limit. It is the entry point of the claim capability (CM-C) in care-management.

Out of scope: claim submission, adjudication and payment. Those stay in claim-management until the capability is migrated.

2. Context

  • Owning module com.carepay.care.claim.preauthorization, exposed to other modules only through PreAuthorizationApi (Spring Modulith named interface).
  • Authorization is delegated to askari; every endpoint checks the SpiceDB permission claim/preauthorization#request for the calling principal.
  • Member and provider identifiers are pvault tokens. Raw identifiers never cross the module boundary or reach Kafka.
  • Replaces the manual phone-and-fax approval flow documented in cm-004.

3. Preconditions

IdRequirement
CM-C-101The member holds an ACTIVE policy covering the requested service date.
CM-C-102The provider is contracted for the scheme that funds the benefit, and the contract is effective on the service date.
CM-C-103The calling principal holds request permission on the benefit through askari.

4. Pre-Authorization Lifecycle

A pre-authorization is an aggregate with an explicit state machine. Transitions are the only way the state changes; there is no direct write path.

state machine
# v3 adds PARTIALLY_APPROVED for multi-line-item requests
REQUESTED      -> UNDER_REVIEW | DECLINED
UNDER_REVIEW   -> APPROVED | PARTIALLY_APPROVED | DECLINED
APPROVED       -> EXPIRED | CONSUMED
PARTIALLY_APPROVED -> EXPIRED | CONSUMED
DECLINED       -> (terminal)
  • PARTIALLY_APPROVED — at least one requested line item is approved and at least one is declined. The aggregate keeps a per-line-item decision.
  • EXPIRED — reached automatically 14 days after approval if no claim references the pre-authorization. (v2: 30 days)
  • CONSUMED — a submitted claim referenced the pre-authorization; the reservation is released against the actual claimed amount.

5. API Contract

openapi/claim-preauthorization.yaml
POST /v1/claims/pre-authorizations
  201 Created            PreAuthorizationResponse, Location header
  409 Conflict           an active pre-authorization exists for the
                           (member, benefit, provider) triple
  422 Unprocessable      benefit not covered on the service date

GET  /v1/claims/pre-authorizations/{id}
POST /v1/claims/pre-authorizations/{id}/decision
  200 OK                 decision recorded, emits a domain event
  409 Conflict           state is terminal
request body
{
  "memberToken": "pv_mbr_8f31…",
  "providerToken": "pv_prv_2ac0…",
  "serviceDate": "2026-09-14",
  "lineItems": [
    { "benefitCode": "OUT-CONS", "estimatedAmount": { "currency": "KES", "value": 4500 } }
  ]
}
